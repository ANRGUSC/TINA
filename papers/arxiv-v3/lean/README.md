# Lean formalization of the arXiv v3 manuscript

Machine-checked proofs of the claims in `submissions/arxiv-v3/main-v3.tex` and
`technical-appendices-v3.tex`, built claim by claim on branch `scott-arxiv2-lean`.

The work began on arXiv v2 (`submissions/arxiv-v2/`, which stays in the
repository; until upstream commit `2821560` it was the working draft
`tina-v2-alt`). It moved to arXiv v3 on 2026-11-18, when the co-author's
revision landed with every agreed edit (see "Decisions, 2026-11-18"). This
directory was `papers/arxiv-v2/lean` until then; links to that path, including
the one to `paper-findings-dispositions.md` sent to the co-author, no longer
resolve. Two names still say v2:

- The Lean package and namespace are `TinaV2`. Renaming them would change the
  hash of every approved file.
- The header comments of the frozen files under `TinaV2/Defs/` and
  `TinaV2/Statements/` cite `main-v2.tex`, for the same reason. The ledger
  (`sources`, `claims`, `steps`) holds the v3 files and line numbers, and the
  proof files changed for v3 cite `main-v3.tex`.

The ledger is aligned to the manuscript at commit `12a9b32`
(`python3 tools/ledger.py sql "SELECT * FROM sources"`). When the paper changes
upstream, `ledger.py check` reports which step texts are no longer found; the
steps, line ranges and `sources` rows are then updated through the CLI.

This work starts from the paper text only. It does not read or reuse
`papers/lcss/lean/`.

## Hard constraints

Revised on 2026-11-14, after the co-author's reply to the findings memo (see
"Decisions"). The first version required every proof to be in the paper.

1. **Every Lean lemma mirrors one written step of an English proof**, in the
   same order, with the same dependencies. Lean may not take a route that is
   not written down.
2. **A written proof has one of two homes.**
   - *The paper.* Where the paper proves a claim, the steps are the paper's
     own sentences, stored verbatim and checked against the TeX.
   - *The supplement.* Where the paper states something without proof, or its
     proof skips an argument, the step is written in the ledger and marked
     `supplied`. It is not in the paper, and nothing (the status, the page,
     the generated documents) reports it as if it were.
3. **The paper is asked to change only at statement level**: what is claimed,
   its hypotheses, its definitions. A Lean theorem must follow from hypotheses
   a reader can find in the manuscript. Gaps inside a proof are supplied.
4. **Every point raised gets a disposition**: the paper changes, Lean supplies
   the argument, the Lean statement fixes a reading, or nothing changes; with
   who decided and why.
5. **Everything is tracked in a queryable ledger**: claims and their
   dependencies, written proofs and steps with their home, Lean statements and
   how each differs from the paper's, Lean proof attempts (with success and
   failure notes, branches and retries), paper edits, findings, dispositions,
   and what the end-to-end assembly still assumes.

## The ledger

SQLite, rebuilt in memory from `schema.sql` + `data.sql` on every call, so git
diffs of the ledger are readable and there is no binary file to merge.
`python3 tools/ledger.py db` writes a `.db` copy for the `sqlite3` shell.

| Table | Holds |
|---|---|
| `claims`, `claim_deps` | Every assertion in the paper and what it depends on. IDs C1–C27 match the co-author review ledger; `C7.b` is a sub-claim. Scope is `lean`, `numeric` or `prose`. |
| `proofs`, `steps`, `step_deps` | English proofs, versioned per claim, split into ordered steps. A proof is `in_paper` or `supplement`; a step is `paper` (verbatim TeX) or `supplied` (written for the formalization). Each step lists what it uses. |
| `formalizations`, `statement_deltas` | Lean statements of a claim, versioned: `draft` → `reviewed` → `frozen`. `statement_deltas` lists, one row each, where a Lean statement differs from the paper's: an extra hypothesis, a restriction, a stronger claim, a chosen reading, another form. |
| `attempts`, `step_map` | Lean proof attempts. Each mirrors one English proof; `parent` links retries and simplifications; `step_map` is the step ↔ lemma correspondence. |
| `assembled` | Per claim with a proved attempt: the claims the assembled theorem still takes as hypotheses (written by `assembly`) and the axioms Lean reports (written by `audit`). |
| `edits`, `hunks`, `edit_deps`, `hunk_steps` | Changes to the paper. An edit takes a claim from one proof version to the next; its hunks hold old and new TeX; `hunk_steps` records which steps each hunk adds, rewrites or removes; `edit_deps` orders edits that build on each other. |
| `findings` | Places where the formalization could not follow the paper as written. |
| `dispositions` | What was decided about each numbered point of a finding (`F10.2`) and each claim the paper states without proof (`C8.c/d1`): `paper_edit`, `lean_supplies`, `reading`, `leave` or `undecided`, with who decided, when, why, and whether it has been carried out. |
| `disposition_scope` | Further claims whose statement a decision touches, beyond the one claim the disposition names (the F8 edit rewords the sentence that introduces C14–C16). |
| `frozen_files` | Lean files approved against the paper, each with its hash, who approved it and when (`ledger.py freeze`). |
| `notes` | Append-only log against any ID: success, failure, insight, decision, todo, build. |

Common queries:

```
python3 tools/ledger.py status            # every claim and its state
python3 tools/ledger.py show C7           # proofs, statements, attempts, edits, notes
python3 tools/ledger.py show C7/p1        # the English proof, step by step, with Lean lemmas
python3 tools/ledger.py headline          # the advertised results: statement, proof home, assumptions, axioms
python3 tools/ledger.py dispositions      # every point and what was decided (--open, --md)
python3 tools/ledger.py supplement        # the arguments that are not in the paper
python3 tools/ledger.py docs              # regenerate the two generated documents
python3 tools/ledger.py frontier          # claims ready to prove
python3 tools/ledger.py check             # invariants below; non-zero exit on failure
python3 tools/ledger.py assembly          # regenerate TinaV2/Assembly.lean and what each theorem assumes
python3 tools/ledger.py audit -v          # what each Lean step lemma uses, against step_deps; records axioms
python3 tools/ledger.py sql "SELECT target, body FROM notes WHERE kind = 'failure'"
```

### Progress explorer

`progress/` is a web page over the same ledger: status overview, the advertised
results with their completion record, the claim dependency graph, one page per
claim with the written proof steps next to their Lean lemmas, findings and
decisions, paper edits, and a SQL console. It reads `ledger/schema.sql` and
`ledger/data.sql` directly (SQLite compiled to WebAssembly, vendored in
`progress/vendor/`), so there is no generated data file to keep in step with
the ledger.

```
python3 tools/ledger.py serve             # http://127.0.0.1:8642/progress/
python3 tools/ledger.py site OUTDIR       # static copy for GitHub Pages
```

The Pages workflow (`.github/workflows/publish-reading-guide.yml`) runs `site`
on every push to `main` that touches this directory and publishes the result at
<https://anrgusc.github.io/TINA/arxiv-v3/lean/progress/> (until 2026-11-18:
`…/arxiv-v2/lean/progress/`, which is no longer built). The site build also
records the result of `ledger.py check`, and the page shows a warning when the
ledger and the paper source in that commit disagree.

Colours on the page: two greens for verified (follows the paper; Lean supplies
steps); blue is in progress (statement drafted, statement approved, proof under
way, proved and awaiting audit, proved but still assuming a claim), darker as it
advances; yellow is not started; red is waiting on a decision or a paper edit
(a point with no decision, a paper edit agreed and not yet upstream, a proposed
proof not applied, or a failed attempt with no successor); grey is numeric or
prose. A claim the paper states without proof is not red once the decision is
that Lean supplies the argument. The rules are in `classify()` in
`progress/app.js`.

Claim states: `todo` → `stated` → `proving` → `proved_unaudited` → `verified`
or `verified_supplied`, with `conditional` when the assembled theorem still
assumes an unproved claim, `needs_paper_edit` when the Lean proof mirrors a
proof that is still only proposed for the paper, and `no_written_proof` when
there is neither a paper proof nor a supplement.

**What verified requires.** The statement is frozen; every step of the mirrored
proof is proved; the assembly assumes no unproved claim (`assembled.assumes` is
empty); Lean reports only `propext`, `Classical.choice` and `Quot.sound`.
`verified` means every step is the paper's. `verified_supplied` means the
proof is a supplement or contains supplied steps. `ledger.py headline` and the
Results page print this record for each theorem, proposition, lemma and
corollary, next to the differences between the Lean statement and the paper's.

## The 1:1 rule

The unit of correspondence is the proof step.

- An attempt file `Proofs/C07/A1.lean` contains one lemma per step of the
  English proof it mirrors (`s1_…`, `s2_…`, in order) and a `main` that combines
  them into `C07.Statement`. It contains nothing else.
- A step lemma states the intermediate fact the written step states. Its proof
  may use only the earlier steps and claims listed for that step in
  `step_deps`, Mathlib, and `TinaV2/Routine/`.
- **A step may cite a step of another claim's proof, if the paper's sentence
  does** (Scott, 2026-11-18). The proof of the stale-global corollary reads
  "This makes the first term in Eq. (innovation_split) zero, its minimum, so
  the regret is half the innovation energy in Eq. (innovation_energy)". Both
  equations are inside the proof of the composition theorem: they are steps 3
  and 4 of `C7/p1`, not the theorem's statement. So `C8/p2/s2` lists
  `C7/p1/s3` and `C7/p1/s4` in `step_deps`, and `Proofs/C08/A2.lean` imports
  `TinaV2.Proofs.C07.A1` and uses the two step lemmas. Such a dependency must
  name a step of the primary in-paper proof of a claim the citing claim uses;
  the import must be the selected attempt of that proof; and `audit` compares
  the lemmas actually used with the steps listed, as for any other step. This
  is the only case so far. The alternative, making the two equations
  sub-claims of C7 with their own statements, was not taken.
- A step is `paper` or `supplied`. A paper step is a sentence of the paper,
  verbatim. A supplied step is a sentence written for the formalization: every
  step of a supplement proof, or a step inserted into a paper proof where the
  paper skips an argument that deserves a sentence.
- `Routine/` holds only what a careful paper leaves unsaid: measurability,
  integrability, finiteness, unfolding definitions, ring identities. It may not
  import `Statements/` or `Proofs/`. Anything that would deserve a sentence in
  the paper is not routine: it is a finding with a disposition, and usually a
  supplied step.

`ledger.py check` enforces what can be checked mechanically:

- every paper step of an in-paper proof is still found verbatim in the TeX;
- every step has exactly one Lean lemma and every lemma in an attempt file has
  a step;
- every Lean statement in the ledger is declared in the file the ledger names;
- a proved attempt has no `sorry` and all its steps proved;
- every step of a supplement proof is marked `supplied`, a supplement proof has
  a `lean_supplies` disposition on its claim, and a supplied step inside a
  paper proof has a disposition pointing at it;
- every open finding has a disposition, and so does every claim the paper
  states without proof;
- a disposition marked done is backed by what it names: a proved supplied
  step, a proved supplement proof, an existing Lean declaration, or an upstream
  commit;
- a proposed proof has an edit carrying its text, and every step that differs
  from the previous proof version is covered by a hunk;
- proposed hunks still apply and applied hunks are present in the TeX;
- at most one primary in-paper proof, one primary supplement and one selected
  attempt per claim;
- a step dependency names an earlier step of the same proof, or a step of the
  primary in-paper proof of a claim this one uses (the cross-proof case above);
- an attempt file imports only `TinaV2.Statements` and `TinaV2.Routine.*`, plus
  the selected attempt file of a proof that owns a step listed as a cross-proof
  dependency; no routine file imports statements or proofs;
- `TinaV2/Assembly.lean` is the file the selected attempts generate, the
  `assembled` rows match it, and no assembled theorem uses an axiom outside
  the standard three;
- the two generated documents are current;
- a frozen Lean file still has the hash recorded when it was approved, every
  `Defs/` file it imports is frozen too, and every frozen statement is in such
  a file. `ledger.py freeze TinaV2/Defs/Cost.lean` (or `freeze C7/f1`) records
  the approval and freezes the statements declared in the file; a statement
  file cannot be frozen before all of `Defs/`;
- no frozen statement belongs to a claim with an open paper edit, an undecided
  point, or a reading its Lean statement does not carry yet
  (`v_freeze_blockers`, which also follows `disposition_scope`). `freeze`
  refuses such a statement and `ledger.py unfreeze C8/f1 REASON` withdraws an
  approval.

`ledger.py audit` goes one level deeper and needs a built project
(`lake build`). Lean lists, for every step lemma of every selected attempt, the
other step lemmas and the claim statements its proof term refers to, looking
through compiler-generated auxiliaries. A step lemma may refer only to the
steps listed for its paper step in `step_deps`, and to the claims those steps
list. So a step cannot quietly use something the paper's step does not. With
`-v` it also prints dependencies that are listed but not used. The map from
Lean lemma to step covers every selected attempt, so a step lemma of another
proof is recognized and must be listed (`C8/p2/s2: uses C7/p1/s3, C7/p1/s4,
C8/p2/s1`). The finished proof of another claim (its `main`) is never allowed:
a claim is used through its statement.

One thing needs more than this and is planned (phase 5):

- a generated side-by-side page (step TeX next to the Lean lemma statement) for
  human review, because whether a Lean statement says what the English says
  cannot be checked by machine.

### When Lean cannot follow the paper

1. Log a `failure` note on the attempt with the obstacle.
2. Open a finding, with one disposition per numbered point (`undecided` until
   someone decides).
3. Triage by level.
   - **Statement level** (a missing hypothesis, an undefined term, a claim
     wider than its proof): this goes to the co-author. If the paper will
     change, the disposition is `paper_edit` and stays open until the edit is
     upstream. If it will not, the disposition is `reading`, and the difference
     is a `statement_deltas` row on the Lean statement.
   - **Proof level** (an argument the paper skips, a whole proof it omits): the
     disposition is `lean_supplies`. Write the argument as a supplied step, or
     as a supplement proof (`C5/p1`, status `supplement`), then mirror it in
     Lean. The co-author is told, not asked.
   - **Wording**: `leave`, unless the co-author wants it.
4. A claim proved this way becomes `verified_supplied`, not `verified`.

Paper edits come in two ways. The co-author edits the manuscript upstream:
the ledger is realigned to the new text, sentences that are now in the paper
become paper steps, and the disposition is marked done with the commit. Or an
edit is written here as diff hunks (`edits`, `hunks`), with a `proposed` proof
version; `ledger.py edit-apply E1` applies it on approval. The second path is
unused so far. The one row in `edits`, `E1`, records an upstream edit: arXiv v3
replaced the proof of the stale-global corollary, and a new proof version
(`C8/p2`, revising `C8/p1`) has to trace to the text that changed.

A simpler proof found along the way is a new proof version. There are two
kinds of branch, and the ledger keeps them apart:

- **Lean-only retry**: same English proof, different tactics. New attempt,
  `parent` set, no change to any written proof.
- **Proof change**: a new proof version. For a supplement proof that is a new
  row; for a paper proof it needs an edit.

## Are separable per-claim proofs safe?

Yes, with the structure below, and the end-to-end check is cheap enough to run
on every commit instead of saving it for the end.

- `Statements/Cxx.lean` defines `Cxx.Statement : Prop` from `Defs/` only.
- A proof file imports `Prelude`, `Defs`, `Statements` and `Routine`. Where the
  paper's step uses claim X, the step lemma takes `(hX : CX.Statement)` as a
  hypothesis. It does not import another claim's proof, with one declared
  exception: `Proofs/C08/A2.lean` imports `Proofs/C07/A1.lean`, because the
  paper's proof of C8 cites two equations inside the proof of C7 (see "The 1:1
  rule").
- `Assembly.lean` is generated from the selected attempts. It supplies each
  hypothesis with the proved theorem (`theorem C10 : C10.Statement :=
  C10.A1.main C08`) and prints the axioms each result depends on.

Editing one proof therefore rebuilds one file, except that a new attempt for
C7 would also mean a new attempt for C8. A stuck upstream proof does not
block downstream work, and attempts for the same claim coexist as separate
files with the same target.

| How separable proofs could leak | What closes it |
|---|---|
| Downstream assumes a different statement than upstream proved | Both refer to the same `Cxx.Statement` constant; `Assembly.lean` fails to type-check otherwise. |
| Each file defines its own version of regret, architecture, etc. | Definitions live only in `Defs/`; proof files may not define model objects. |
| `sorry` or added axioms | `check` rejects `sorry`; `audit` records the axioms of each assembled theorem and `check` rejects any outside the three standard ones. |
| The hardest step is supplied as a hypothesis | `assembly` records which unproved claims each assembled theorem still assumes; such a claim is `conditional`, never `verified`. |
| Lean proves it by an argument that is nowhere written | Every lemma in an attempt maps to a written step; supplied steps are marked and listed in `supplement.md`. |
| A proof reaches into another claim's proof file | `check` allows the import only for a cross-proof step dependency recorded in `step_deps`; `audit` allows only the listed step lemmas and never the other proof's `main`. |
| Circular dependence between claims | Assembly order follows the claim graph; Lean rejects import cycles. |
| A statement is vacuous (hypotheses cannot all hold) | Each model gets a concrete instance satisfying its hypotheses (phase 5). |
| The Lean statement is not the paper's statement | `statement_deltas` lists the known differences; human review against them, then `frozen`. A later change is a new formalization version, and the ledger shows which attempts it invalidates. |

## Working rules

- Before an attempt, run `ledger.py show <claim>` and read the failure notes.
- Test the exact statement numerically before trying to prove it.
- Search Mathlib (`.lake/packages/mathlib`) before writing a `Routine` lemma.
- Never `import Mathlib` whole: it costs about 48 s per file check here, against
  about 4 s with the narrow list in `Prelude.lean`. Add modules there as needed.
- If a step is not closed after about eight build cycles, stop, log a `failure`
  note naming the obstacle, and choose between a Lean-only retry and a finding.
- Record build time and line count on every proved attempt, so variants can be
  compared.
- Run `ledger.py check` before every commit.
